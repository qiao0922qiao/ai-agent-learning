Skill（智能体技能）

一句话定位：把"某类任务怎么做"写成文件夹沉淀下来，让 Agent 随用随取的标准化方式。
概念领域：AI Agent 工程 ｜ 生成日期：2026-09-06 ｜ 由 learning-material-generator Skill 生成，经人工核查修改

1. 学习目标

  • 能解释"渐进式披露"（progressive disclosure）为什么是 Skill 的核心设计
  • 能区分 Skill 与提示词、微调、MCP 工具这三种扩展 Agent 能力的方式
  • 能说出项目级 Skill 与用户级 Skill 的存放位置区别
  • 能自己动手为一个重复性任务写一个 Skill

2. 核心问题

  1. 为什么不直接把"怎么做"写进提示词，而要做成 Skill 文件夹？
  2. Skill 是怎么做到"装了几百个也不撑爆上下文"的？
  3. Skill 和工具（Tools）、微调（Fine-tuning）各自解决什么问题？

3. 我的理解（个人解释）

我是这样理解的：Skill 就是给 Agent 的岗位操作手册（SOP）。新员工（通用大模型）脑子很聪明，但不了解你公司的规矩和流程。你有两种选择：每次布置任务都口头交代一遍全部注意事项（每次手写长提示词），或者干脆把"这类任务的标准流程"写成一册手册放进公司资料柜（创建 Skill）——以后只要说"按 XX 手册办"，新员工自己去取、照着做。

妙处在于手册的目录页设计（渐进式披露）：资料柜里每本手册只有封面目录常驻 Agent 的"便签纸"（上下文）——也就是 SKILL.md 开头的 name 和 description，只占几十个 token；等真正接到相关任务，Agent 才翻到正文（读完整的 SKILL.md）；正文里引用的附录（references/、scripts/ 等附加文件）更是用到才读。所以装一百本手册的目录成本很低，但需要时专业知识能精确到位。这样，"任务知识"就从聊天记录里的易失信息，变成了可以用 Git 管理版本、可以分享给同学和团队的沉淀资产。

本仓库里的这个学习资料生成器本身就是一个 Skill（就是一份"如何学概念"的操作手册），用它的过程就是在验证这个概念——这就是我理解的"用 Skill 沉淀可复用的任务知识"。

4. 核心机制 / 组成

一个 Skill 的标准形态是一个文件夹：

my-skill/
├── SKILL.md        # 必需：YAML 元数据（name、description）+ 具体指令
├── references/     # 可选：更详细的参考文档，用到才读
├── scripts/        # 可选：可执行的脚本（Agent 可直接运行，不必读进上下文）
└── assets/         # 可选：模板、素材等资源

SKILL.md 开头的 YAML 元数据（必需字段）：

---
name: my-skill-name        # 小写字母/数字/短横线
description: 做什么 + 什么时候用   # Agent 判断"要不要激活"的唯一线索
---

核心机制——渐进式披露（三级加载）：

层级加载时机占用上下文
① 元数据（name + description）会话启动时常驻约几十 token / 个
② SKILL.md 正文任务匹配时 Agent 主动读取约几百 token
③ 附属文件（references / scripts）执行中按需读取或直接运行2000+ token，仅在需要时

注：Agent Skills 格式由 Anthropic 提出，已于 2025 年 12 月作为开放标准发布（skill.md），可跨平台使用。存放位置分两级：用户级（如 ~/.workbuddy/skills/，个人全局可用）与项目级（仓库内 .workbuddy/skills/，随项目共享给团队）。

5. 具体应用场景

场景：本作业的概念学习流水线。

不写 Skill 时，我每次学新概念都要重新口述一遍要求："要有个人的理解、要有应用场景、要查真实资料、要有自测题、存成 HTML……"——换个概念再说一遍，且质量随口述详略波动。写成本仓库的 learning-material-generator Skill 之后：学习流程（步骤、输出结构、来源要求、自检清单）被固定在 SKILL.md 里，我只要说"用 learning-material-generator 学一下 RAG"，Agent 激活 Skill、按同一套标准执行。以后还能继续迭代这份"手册"（比如加"生成思维导图"小节），所有改进都沉淀在版本库里，而不是散落在历次对话里。

6. 概念辨析（易混淆点与边界）

易混淆项区别边界：什么时候不是 Skill
Skill vs 提示词 提示词是单次任务的一次性指令；Skill 是可复用、可版本化、带元数据的"指令资产"，由 Agent 按需自动激活 只在一个对话里用一次、没有文件夹与元数据形态的指令，只是提示词
Skill vs 微调 Skill 改变"模型能看到的操作知识"（推理时注入上下文）；微调改变模型参数本身（重新训练） 需要重新训练模型、更新权重才能获得的能力不是 Skill；Skill 不碰模型参数
Skill vs 工具 / MCP 工具/MCP 给 Agent 接入"外部能力"（搜索、发邮件等 API）；Skill 给 Agent 注入"做事的方法与流程知识"（know-how） 单纯暴露一个 API/功能让模型调用的是工具；组织"何时、如何做好一类任务"的文件才是 Skill

使用边界（重要）：Skill 适合重复出现的流程性任务（固定格式输出、固定检查清单、固定工作流）。一次性的、高度个性化的任务，直接对话描述即可，强行做成 Skill 反而增加维护负担。另外，Skill 来自不可信来源时有安全风险（恶意指令可能引导 Agent 执行危险操作），应只使用自己编写或可信来源的 Skill。

7. 自测问题

Q1：SKILL.md 顶部的 YAML 元数据必须包含哪两个字段？它们各自的作用？

参考答案：name 和 description。name 是 Skill 的唯一标识（小写字母/数字/短横线）；description 说明"做什么 + 什么时候用"，是 Agent 判断是否激活该 Skill 的唯一线索，因此必须写清适用场景。

Q2：装了 100 个 Skill 为什么不会撑爆上下文？

参考答案：渐进式披露：会话启动时只把每个 Skill 的 name + description（约几十 token）放进系统提示；正文只在任务匹配时读取；附属文件用到才加载。常驻成本极低。

Q3：项目级 Skill 和用户级 Skill 分别放在哪里？各有何适用场景？

参考答案：用户级放在用户主目录（如 ~/.workbuddy/skills/），跨项目个人可用；项目级放在仓库根目录 .workbuddy/skills/，随代码仓库共享给所有协作者。团队通用流程适合项目级，个人习惯适合用户级。

Q4：想让 Agent 掌握"公司财报排版规范"，Skill 和微调该选哪个？为什么？

参考答案：Skill。排版规范是流程性知识（规则、模板、步骤），写进 SKILL.md 即可随用随取、随时修改、无需训练；微调成本高、周期长、改规范要重训，且不适合承载精确遵循的规则类知识。

Q5：为什么说 Skill 是"可沉淀的任务知识"，而对话不是？

参考答案：对话内容散落在各次会话中，难以复用和迭代；Skill 以文件形式存在，可用 Git 做版本管理、可复制分享、可持续改进——知识从"一次性口头交代"变成"可维护的资产"。
